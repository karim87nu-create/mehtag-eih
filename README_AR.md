# Request Spike v0.1

الهدف من المشروع: إثبات المسار التالي بدون Marketplace وبدون تسجيل تاجر مسبق:

طلب العميل → فهم مبدئي → اكتشاف منفذين → إنشاء رابط طلب للتاجر → التاجر يرسل عرضًا → العرض يظهر للعميل/الإدارة.

## المطلوب منك فقط

1. فك الضغط.
2. افتح Terminal داخل المجلد.
3. شغّل:
   - Windows:
     `python -m venv .venv`
     `.venv\Scripts\activate`
   - ثم:
     `pip install -r requirements.txt`
     `uvicorn app.main:app --reload`
4. افتح:
   `http://127.0.0.1:8000`

## Google Places

المشروع يعمل بدون Google Places في وضع تجريبي داخلي.

للتجربة الحقيقية:
- انسخ `.env.example` إلى `.env`
- ضع مفتاح Google Places API في:
  `GOOGLE_PLACES_API_KEY=...`

عند وجود المفتاح، النظام يستخدم Google Places Text Search لاكتشاف أنشطة حقيقية.

## مهم

هذه النسخة لا ترسل رسائل باردة إلى التجار تلقائيًا، لأن قناة First Contact يجب أن تكون قانونية/مسموحة ومؤكدة لكل قناة.
لكنها تبني الجزء الذي نحتاجه الآن:
- Request
- Discovery
- Merchant request link
- No-login offer
- Events
- Offer collection
- Basic matching

مسار الإرسال الخارجي موجود كنقطة ربط `send_request_to_endpoint()` ليتم توصيله لاحقًا بقناة مصرح بها.

## صفحات مهمة

- `/` واجهة العميل
- `/admin` الطلبات والعروض
- `/r/{token}` صفحة التاجر بدون تسجيل

## معيار نجاح Gate A

طلب حقيقي → منفذ لم يكن مسجلًا مسبقًا → يفتح رابط الطلب → يرسل عرضًا → العرض يظهر بالنظام
وذلك بدون إدخال العرض يدويًا من فريق التشغيل.

# Stage 1 Complete — قلب المنتج
هذه الحزمة تجمع تعديلات v0.1 إلى v0.15 وتغلق المرحلة الأولى كحزمة واحدة.

### ما تم إقفاله
- واجهة عميل واحدة «محتاج إيه؟» بدون فئات/Marketplace.
- تصنيف أولي للطلب: DIRECTED / REMEMBERED / OPEN.
- استخراج قيود أساسية: الميزانية، المنطقة، الموعد، والجهة المذكورة.
- Outcome Memory + تفضيلات لا تصبح قاعدة إلا بعد تكرار ثم موافقة العميل.
- التفضيلات المؤكدة تدخل في الطلب الجديد ولا تتغلب على تعليمات العميل الحالية.
- ترتيب عروض شفاف يعتمد على الملاءمة وسجل النتائج، وليس Pay-to-Rank.
- رسم خدمة ظاهر قبل «خلّصهالي» وعلى مستوى العملية، وليس على كل رسالة.
- Execution Case من الاختيار إلى التنفيذ ثم تأكيد النتيجة.
- مشكلة العميل لا تغلق العملية؛ لها دورة OPEN → حل مقترح → تأكيد العميل → VERIFIED.
- أي تغيير سعر/موعد بعد الاختيار يحتاج موافقة العميل.
- اكتشاف تعاملات خارجية، منع التكرار، وربط تحديثات نفس التعامل.
- Follow-up Tasks للأحداث التي تستحق متابعة.
- سجل أداء المنفذ يتأثر بالنتيجة المؤكدة.

### ما لم يتم تزويره
- الدفع ما زال محاكاة.
- الوصول الخارجي لتاجر مجهول لم يُعتبر ناجحًا بعد.
- البريد/APIs/Android ليست متصلة Live بعد.
- القيم الحالية لرسم الخدمة تجريبية وليست تسعيرًا نهائيًا.

### المرحلة التالية
Stage 2 = قلب السوق والتاجر: discovery → lawful reachability → first request without prior account → offer → acceptance → capability history.
